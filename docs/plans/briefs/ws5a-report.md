## Public signatures WS5b / WS4 / WS7 will use

### Domain (`com.llmlocal.recipekeeper.domain`)

```kotlin
data class ClippedRecipe(id, title, description?, servings?, prepMinutes?, cookMinutes?, totalMinutes?,
    ingredients: List<String>, steps: List<String>, notes?, sourceUrl, sourceHost, pictures: List<String> /* abs. local paths, [0] = hero */,
    truncated: Boolean, clippedAt: Long, checkedIngredients: Set<Int> = emptySet())          // unchanged
data class RecipeSummary(id, title, sourceHost, totalMinutes?, heroPicture?, truncated, clippedAt)   // unchanged
data class RecipeDraft(title?, description?, servings?, prepMinutes?, cookMinutes?, ingredients, steps, notes?, tail)  // unchanged

interface RecipeRepository {
    fun observeAll(): Flow<List<RecipeSummary>>          // non-deleted, newest first
    fun observe(id: String): Flow<ClippedRecipe?>        // soft-deleted INCLUDED (detail keeps rendering during the undo window)
    suspend fun upsert(recipe: ClippedRecipe)
    suspend fun softDelete(id: String)                   // NEW
    suspend fun restore(id: String)                      // NEW
    suspend fun delete(id: String)                       // hard delete: row + picture rows (cascade) + picture folder
    suspend fun purgeDeleted(olderThanMillis: Long): List<String>   // NEW — call at app start with now - 5_000
    suspend fun setChecked(id: String, checked: Set<Int>)
    fun search(query: String): Flow<List<RecipeSummary>> // title OR ingredients LIKE; blank query == observeAll()
}
```

**Undo-delete flow for WS5b:** `softDelete(id)` → pop + snackbar "Deleted · Undo" (5 s) → on timeout `delete(id)`, on Undo `restore(id)`. `RecipeKeeperApp.onCreate` (WS5b) should call `purgeDeleted(System.currentTimeMillis() - 5_000)` once (off main thread) to clean up after process death inside the window.

### Room (`com.llmlocal.recipekeeper.data`)

```kotlin
@Entity("recipes", indices = [clippedAt, deletedAt])
data class RecipeEntity(@PrimaryKey id: String, title: String, description: String?, servings: String?, prepMinutes: Int?, cookMinutes: Int?,
    totalMinutes: Int?, ingredients: List<String> /* JSON */, steps: List<String> /* JSON */, notes: String?, sourceUrl: String, sourceHost: String,
    truncated: Boolean, clippedAt: Long, checkedIngredients: Set<Int> /* JSON */, deletedAt: Long? /* null = live */)

@Entity("pictures", primaryKeys = [recipeId, position], FK recipes.id ON DELETE CASCADE, index recipeId)
data class PictureEntity(recipeId: String, position: Int /* 0 = hero */, path: String /* absolute */)

data class RecipeWithPictures(@Embedded recipe: RecipeEntity, @Relation pictures: List<PictureEntity>)
data class RecipeSummaryRow(id, title, sourceHost, totalMinutes?, heroPicture?, truncated, clippedAt)

@Dao interface RecipeDao {
    fun observeSummaries(): Flow<List<RecipeSummaryRow>>                  // deletedAt IS NULL, ORDER BY clippedAt DESC, hero via sub-select
    fun searchSummaries(query: String): Flow<List<RecipeSummaryRow>>      // + title/ingredients LIKE '%q%'
    @Transaction fun observeWithPictures(id: String): Flow<RecipeWithPictures?>
    @Transaction suspend fun getWithPictures(id: String): RecipeWithPictures?
    @Upsert suspend fun upsert(entity: RecipeEntity)
    suspend fun insertPictures(pictures: List<PictureEntity>); suspend fun deletePictures(recipeId: String)
    @Transaction suspend fun upsertWithPictures(entity: RecipeEntity, pictures: List<PictureEntity>)   // replaces the picture list
    suspend fun delete(id: String)                                        // hard; pictures cascade
    suspend fun setDeletedAt(id: String, deletedAt: Long?)
    suspend fun deletedBefore(olderThan: Long): List<String>
    suspend fun setChecked(id: String, checked: Set<Int>)
    suspend fun deletedAtOf(id: String): Long?
}
abstract class RecipeKeeperDatabase : RoomDatabase { abstract fun recipeDao(): RecipeDao; companion object { const val NAME = "recipekeeper.db" } }
class RecipePictureStore(root: File) { fun dirFor(id): File; fun moveIn(id, files: List<File>): List<String>; fun deleteAll(id) }
class RoomRecipeRepository(dao, pictures: RecipePictureStore, dispatchers: DispatcherProvider, clock: () -> Long = System::currentTimeMillis) : RecipeRepository
```

Decision: pictures are a **separate table**, not a JSON column — the list summary gets the hero through one sub-select and the sink replaces the list atomically in `upsertWithPictures`. Ingredients/steps/checked are JSON columns so the `LIKE` search works without another table. Schema version stays **1** (WS0's trivial table never shipped; the exported `1.json` was replaced, no migration).

### Clip (`com.llmlocal.recipekeeper.clip`)

```kotlin
class SchemaOrgRecipeMapper(durationParser: (String?) -> Int? = IsoDuration::toMinutes) {
    fun map(node: JsonLdNode, sourceUrl: String, id: String = UUID, clippedAt: Long = now): ClippedRecipe?   // null when no ingredients AND no steps
    fun name(raw); fun description(raw); fun ingredients(raw); fun instructions(raw); fun imageUrls(raw); fun yieldText(raw)
    fun minutes(raw, key); fun totalMinutes(raw, prep?, cook?)
}
class RecipeKeeperClipConfig(durationParser = IsoDuration::toMinutes, mapper = SchemaOrgRecipeMapper(durationParser),
    idFactory: () -> String = UUID, clock: () -> Long = now) : WebClipConfig<ClippedRecipe> {
    companion object { MAX_CANDIDATES = 10; WHOLE_PAGE_ID = "page"; TRUNCATION_MARKER = "\n[…truncated]"; MIN_QUANTITY_LINES = 3; MIN_WHOLE_PAGE_CHARS = 500 }
}
class RecipeKeeperClipSink(repository, pictures: RecipePictureStore, dispatchers, idFactory = UUID, clock = now) : ClipSink<ClippedRecipe>
val RecipeKeeperTaskConfig: LlmTaskConfig<ClippedRecipe>
```

Candidate ids: `structured-<n>`, `text-<n>`, `page` (WholePage). `detect` returns STRUCTURED (document order) → else TEXT (by heading level, then position) → else one WholePage when readable ≥ 500 chars → else empty. **WS4:** for "Extract anyway" build the WholePage candidate yourself or call `detect` on a snapshot — `pickPictures`/`renderLlmInput` accept any candidate with `CandidatePayload.WholePage`.

`renderLlmInput` always starts with `Page: <host> — <title>` (the §3.4 user-prompt header lives here because `PromptBuilder.userPrompt` only receives the rendered input), then the body trimmed at a paragraph boundary to `budgetChars` with `TRUNCATION_MARKER`. Rendered STRUCTURED input for a typical recipe is ~600–900 chars.

### Parsers / prompt

```kotlin
class RecipeKeeperPromptBuilder : PromptBuilder            // companion SYSTEM; userPrompt = "Extract the recipe from this page.\n\n" + inputs
class RecipeKeeperParser : TaskParser<ClippedRecipe>       // null when no ingredients and no steps
class RecipeKeeperDraftParser { fun parse(streamedText: String): RecipeDraft }   // never null
```

**Detached results — important for WS4/WS5b:** `RecipeKeeperParser` cannot know the page, so it returns `id = ""`, `sourceUrl = ""`, `sourceHost = ""`, `pictures = []`, `clippedAt = 0`, and `title = ""` when the model omitted it. `RecipeKeeperClipSink.save` fills them (id minted unless non-blank, title ← `candidate.title` ← `snapshot.title` ← "Untitled recipe", `truncated = item.truncated || truncated`). The deterministic `fallback()` result is already attached (id from `idFactory`, source URL from the snapshot) and the sink keeps its id. Anything that renders a parsed-but-unsaved `ClippedRecipe` must tolerate the blanks.

`ClippedRecipe.truncated` from the parser is a heuristic (output ends inside Steps without terminal punctuation); the ViewModel's token-cap check is OR-ed in by the sink.

Request options (temperature 0.2, `maxOutputTokens = config.maxOutputTokens`) are **not** in the prompt text; WS4's `ExtractionViewModel` sets them on `LlmRequest`.

## Decisions recorded

1. Pictures table instead of JSON column (hero sub-select, atomic replace).
2. Soft delete lives in the data layer (`deletedAt`); the domain exposes three verbs instead of a flag on `ClippedRecipe`.
3. `Page: host — title` header is part of `renderLlmInput`, not the prompt builder (contract constraint).
4. Tier B: an "Ingredients" h3 is titled by its nearest shallower non-ingredient heading; nested sections after a candidate are not re-offered as candidates; rendering a TEXT candidate pulls in following deeper/sibling instruction and notes sections and stops at the next recipe or a parent heading.
5. URL path boost = quantity-line threshold 3 → 2 (a boost needs a comparator; one page has one URL).
6. Parser returns a detached recipe; the sink attaches page metadata (keeps `TaskParser<ClippedRecipe>` unchanged).
