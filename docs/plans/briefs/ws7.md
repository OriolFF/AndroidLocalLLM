# Brief — WS7: local evaluation harness (standard pipeline vs the real model)
Read `docs/plans/briefs/_common.md` first (your base is `recipekeeper/main`, which now contains WS0, WS1, WS2, WS3 and WS5a), then `docs/plans/recipekeeper-app-plan.md` decision A16 and **WS7** in section 4, `docs/plans/briefs/ws2-report.md` (capture.js output schema, jsdom harness under `core/web/tools/capture-harness/`), `docs/plans/briefs/ws5a-report.md` (public signatures of `RecipeKeeperClipConfig`, `RecipeKeeperPromptBuilder`, `RecipeKeeperParser`, `SchemaOrgRecipeMapper`), and `docs/plans/recipekeeper-research-notes.md` §A (LiteRT-LM API, the WS1 spike addendum, CPU speed estimates).

**You own:** `app/recipekeeper/src/test/kotlin/com/llmlocal/recipekeeper/eval/**`, `app/recipekeeper/src/test/resources/eval/**`, `app/recipekeeper/src/androidTest/**`, `tools/eval/**`, and `app/recipekeeper/build.gradle.kts` only for androidTest deps. Do not change production code; if a production bug blocks you, document it in the report with a proposed patch instead.

Goal: measure how the **standard pipeline** (`detect` → `renderLlmInput` → `RecipeKeeperPromptBuilder` → model → `RecipeKeeperParser`) performs against the **same Gemma 4 E2B `.litertlm` file the app uses**, and turn the results into repeatable tests plus a report that answers plan decision #3 (should structured pages skip the model?).

Steps:
1. **Fixtures.** Produce 8–10 `PageSnapshot` JSON files under `src/test/resources/eval/pages/` using WS2's jsdom harness (`core/web/tools/capture-harness/harness.mjs`; install `jsdom` in a scratch dir, not in the repo) against saved HTML of real pages you fetch with `curl -L -A "Mozilla/5.0"` into `tools/eval/html/` (commit the HTML only if ≤ 300 KB each; otherwise keep the JSON snapshot and record the URL + fetch date in `README.md`). Cover: JSON-LD single recipe; `@graph`; round-up with 3+ recipes; HowToSection instructions; plain-text blog without structured data; a non-English recipe page; a list/category page with no recipe; a very long page (> 9,000 chars of readable text). No network access from tests.
2. **`EvalPromptRenderingTest`** (JVM): for each fixture, load the snapshot (reuse `PageSnapshotMapper.fromJson` via a tiny copy or by making a test-only accessor — it is `internal` in `:core:web`, so copy the minimal mapping into the test or read the JSON into `PageSnapshot` directly), run `RecipeKeeperClipConfig.detect`, assert expected candidate counts/tiers per fixture, run `renderLlmInput` for the top candidate, assert length ≤ `budgetChars`, build the full prompt with `RecipeKeeperPromptBuilder` exactly as `LlmTaskRepositoryImpl` does, and write it to `build/eval/prompts/<fixture>.txt`.
3. **Runner.** `tools/eval/run_local_model.sh` runs every prompt in `build/eval/prompts/` through LiteRT-LM and writes `src/test/resources/eval/outputs/<fixture>.txt` plus `outputs/<fixture>.timing.json` (TTFT and total ms, token counts if available). Preferred path (a): a desktop LiteRT-LM runtime on this Mac — check `pip index versions litert-lm` / `uv pip install litert-lm` in a scratch venv, or a `litert-lm` CLI binary from the GitHub releases page; it must load `.litertlm` bundles on macOS CPU. Fallback (b): `adb`-driven instrumented runner — `app/recipekeeper/src/androidTest/.../EvalRunnerTest.kt` reads prompts from an `adb push`ed directory (`/sdcard/Download/eval/prompts`), runs `LiteRtLlmEngine` (CPU) against the model already installed in the app's `files/llm/`, writes outputs next to them, and the script pulls them back. **Device constraints:** `emulator-5554` has ~220 MB free and no model; a real arm64 phone with the model downloaded via the Recipe Keeper or Recipes app is required for path (b). If neither (a) nor (b) is possible right now, implement the script and the runner anyway, verify them as far as you can (dry run, `--help`, instrumented test compiles), and say exactly what remains.
4. **`EvalParserTest`** (JVM, must run in CI without the model): for every fixture that has a committed golden in `outputs/`, parse with `RecipeKeeperParser` and `RecipeKeeperDraftParser` (every prefix monotonic), assert: title non-empty, ≥ 3 ingredients, ≥ 2 steps, ingredient count within ±20% of the JSON-LD count when available, servings/time present when the source has them, no hallucinated section headers, and for STRUCTURED fixtures Jaccard ≥ 0.8 between parsed ingredients and `SchemaOrgRecipeMapper` ingredients (normalised lower-case tokens). Fixtures without a golden are skipped with an explicit assumption message, not failed.
5. **Report generator**: the parser test also writes `build/eval/report.md` (per fixture: tier, prompt chars, parse ok/fail, field coverage, TTFT/total from the timing JSON when present) and a summary line per tier. Commit a copy as `docs/plans/briefs/ws7-eval-report.md` whenever goldens exist.
6. Document the re-run loop in `tools/eval/README.md`: `./gradlew :app:recipekeeper:testDebugUnitTest --tests '*EvalPromptRenderingTest*' && tools/eval/run_local_model.sh && ./gradlew :app:recipekeeper:testDebugUnitTest --tests '*EvalParserTest*'`.
Done when: fixtures + rendering test green, runner script and instrumented runner exist and are documented, parser test green (skipping fixtures without goldens), report written with the recommendation for decision #3 or the exact blocker (model/device) that prevents it.
