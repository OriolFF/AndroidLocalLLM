# Brief — research: sharing on-device LLM model files across Android apps
You are a **research agent** (no code changes, no `git` writes). Context: this repo is a white-label Android template where every app (`:app:recipes`, `:app:medical`, `:app:recipekeeper`) downloads its own copy of a 2.6 GB `.litertlm` model into its private `filesDir/llm/`. Three installed apps = three downloads and 7.8 GB. Read `CLAUDE.md` (sections "Models: catalog, selection, download" and "LiteRtLlmEngine") and `core/llm/src/main/kotlin/com/llmlocal/core/llm/download/LlmModelManager.kt` + `core/llm/src/main/kotlin/com/llmlocal/core/llm/engine/LiteRtLlmEngine.kt` to understand how models are stored and opened today (`EngineConfig(modelPath = file.absolutePath, …)`).

Research question: **how can several of our apps (same developer, same signing key, installed independently from Play or sideloaded) share one model file on Android 7–16, so the model is downloaded once and reused by all, with safe lifecycle (deletion when the last user uninstalls, updates, integrity)?** Use web search / official docs (developer.android.com, AOSP, LiteRT-LM GitHub and docs) and cite sources. Today is 2026-10-19; prefer current docs and check Android 15/16 changes.

Cover at least these options, with for each: how it works, API level support, permissions/user prompts, whether LiteRT-LM can open the model that way (it wants a file path — check whether `/proc/self/fd/<n>` from a `ParcelFileDescriptor` works, whether the engine mmaps, and whether LiteRT-LM has any fd/AssetFileDescriptor API in 0.18.0), performance (mmap vs copy), security (who else can read it), Play policy implications, and lifecycle (orphan cleanup):
1. **`BlobStoreManager`** (Android 11+, designed for sharing large blobs like ML models between apps; leases, access modes `allowSameSignatureAccess`/`allowPackageAccess`/`allowPublicAccess`, expiry). Does it return a seekable fd usable by native code? Size limits? Is it available on all OEM builds?
2. **Signature-protected `ContentProvider`** in one "model host" app (or each app able to serve) exposing the file via `openFile` → `ParcelFileDescriptor`; `android:protectionLevel="signature"` permission; `/proc/self/fd` path for the native engine; who hosts when the host app is uninstalled (each app re-hosting / leader election via `PackageManager`).
3. **Shared external storage**: `Downloads/` via `MediaStore.Downloads` + `IS_PENDING`, SAF `ACTION_OPEN_DOCUMENT_TREE`, `MANAGE_EXTERNAL_STORAGE` (Play policy), app-specific external dirs (not shareable), `requestLegacyExternalStorage` (dead). 5. **System/Play solutions**: Play Asset Delivery (per app, not shared), Google **AICore / Gemini Nano / ML Kit GenAI** on-device system models (shared by the OS; which devices, which models, can LiteRT-LM use them? no), Android 16 "AI Core" APIs, Samsung/Qualcomm vendor model stores — is any of this a realistic path for a Gemma `.litertlm`?

7. **Content URIs + `grantUriPermission` ad hoc** vs persistent `FLAG_GRANT_PERSISTABLE_URI_PERMISSION`.
8. Hard links / `Os.link`, symlinks, `/data/local/tmp`, `app-specific dirs on the same volume` — confirm these do not work across app sandboxes (SELinux).
